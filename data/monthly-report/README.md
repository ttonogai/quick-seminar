# 月次報告書ハンズオン用サンプルデータ

「月次報告書：作業実績から報告書を自動生成」シナリオで使うサンプルデータです。

## 想定シナリオ

システム運用保守サービスを提供する会社（運用チーム 4 名）が、顧客 3 社に対して**毎月の運用報告書を提出**しています。現状は、作業実績表（Excel/CSV）から報告書フォーマットへ手作業で転記しており、1 社あたり 3〜4 時間かかっています。

このシナリオでは、実績表・報告書テンプレート・前月の報告書を Space に取り込み、**対象月と顧客名を入れるだけで報告書ドラフトが完成する**状態を作ります。

- 対象期間：2026-04 〜 2026-06（作業実績表は 2026-05・2026-06 の 2 ヶ月分）
- ハンズオンで生成する対象：**2026 年 6 月分 / あさひ物流株式会社**

> データはハンズオン用に生成した**サンプル（フィクション）**です。実在の企業・人物とは関係ありません。

## ファイル一覧

| ファイル | 役割 | 内容 |
|---|---|---|
| `作業実績表.csv` | 集計元データ | 顧客 3 社 × 2 ヶ月分の作業実績 88 行 |
| `月次報告書テンプレート.md` | 出力フォーマット定義 | 全 8 章の章構成・表の列・記載ルール |
| `前月分_月次報告書.md` | 文体・粒度の見本 | 2026 年 5 月分の完成報告書（あさひ物流） |
| `運用実績日次.csv` | ダッシュボード用 | 3 ヶ月 × 3 社の日次集計 273 行 |

## 列の説明

### 作業実績表.csv

| 列 | 説明 |
|---|---|
| 作業ID | 作業の一意キー |
| 対象月 | 報告対象月（YYYY-MM）。報告書生成時の絞り込みキー |
| 顧客名 / 契約プラン | 顧客とその契約プラン（ライト / スタンダード / プレミアム） |
| システム名 | 対象システム。システム別集計に使用 |
| 作業日 | 実施日 |
| 作業種別 | 定期運用 / 監視対応 / インシデント対応 / 変更作業 / 問い合わせ対応 / バックアップ確認 / 改善提案 / レポート作成 |
| 作業内容 | 実施した作業の具体的な内容 |
| 担当者 | 担当エンジニア |
| 作業区分 | 定期 / 突発 |
| 工数_時間 | 作業に要した時間 |
| ステータス | 完了 / 進行中 / 未着手（進行中・未着手は「次月の予定」の材料になる） |
| インシデント番号 | インシデント対応時のみ付与 |
| 重要度 | A（30 分以内初動） / B（60 分） / C（240 分） |
| SLA目標_分 / 初動時間_分 / SLA遵守 | SLA 判定用。`○` が遵守、`×` が未達 |
| 備考 | 補足。再発や SLA 未達の理由が書かれている行がある |

### 運用実績日次.csv

日付 × 顧客の日次集計。`作業件数` `作業工数_時間` `インシデント件数` `監視アラート件数` `問い合わせ件数` `SLA超過件数`。ダッシュボード作成（管理者向けオプション）で使います。2026-04 分は日次のみの補完データです。

## このデータに仕込んである「気づき」

報告書を生成すると、AI が実績から次のような指摘を拾い上げます。手作業の転記では見落としやすい点であり、このシナリオの価値そのものです。

1. **工数の急増**：あさひ物流の総工数が 5 月 54.0 時間 → 6 月 78.5 時間（+45.4%）。要因はインシデント対応（7.5 → 20.0 時間）と本番パッチ適用の集中。
2. **SLA 未達 1 件**：`INC-2606-023`（6/18 22:40 発生）が重要度 A・目標 30 分に対し初動 52 分で未達。備考に「夜間オンコールの応答遅延」と原因が記載されています。
3. **ディスク逼迫の再発**：在庫管理システムで 5/20・6/3・6/17 とディスクアラートが 3 回発生し、6/12 には夜間バッチ異常終了（`INC-2606-022`）、6/27 にはレスポンス遅延（`INC-2606-026`）へ発展。**5 月の報告書で提案した恒久対策（ディスク拡張）が承認待ちのまま再発している**という因果が、前月分報告書と突き合わせることで見えます。
4. **未完了作業が 3 件**：ディスク拡張作業（進行中）、夜間オンコール体制の見直し提案（進行中）、ログローテーション設定の見直し（未着手）。テンプレートの「次月の予定」に自動で起案されます。
5. **問い合わせの減少**：7 件 → 4 件。5 月の報告書で提案した FAQ 整備の効果として読み取れます。
6. **報告書作成そのものの工数**：`OPS-2606-034` に「月次報告書作成（5月分）4.5 時間・実績表からの転記に時間を要した」と記録されています。このシナリオが解決しようとしている課題が、データの中にも入っています。

## 質問例（エージェントのチャットで）

- 2026 年 6 月のあさひ物流の作業実績を、作業種別ごとに件数と工数で集計して
- 6 月に SLA 目標を達成できなかったインシデントはある？原因と再発防止策を教えて
- 在庫管理システムのディスク関連の事象を時系列で並べて、根本原因を推定して
- 5 月と 6 月を比較して、工数が増えた理由を実績データから説明して
- 進行中・未着手の作業を洗い出して、次月の予定として整理して
- 3 社のうち、6 月に最も工数がかかった顧客はどこ？契約プランと見合っているか評価して

## ダッシュボードにする場合（管理者向け）

```
運用実績日次を使って、顧客別の月次工数推移、インシデント件数の推移、
SLA超過の発生状況、問い合わせ件数の推移を可視化する
運用サービス管理ダッシュボードを作って
```
