# 対応記録サンプル

手順書に起こす元ネタとなる、実際の対応記録の想定サンプルです。
**わざと情報が欠けています。** 手順書フォーマットの「【要追記】」がどう働くかを確認するために使います。

---

## 記録 A：SSO 証明書の更新対応

```
対応記録 / INC-2026-0605-01
担当：藤原
受付：2026-06-05 08:47

朝から複数部署でログインできないと連絡。SSOの証明書が切れてた。
IdPの管理画面で確認したら notAfter が 6/5 になってた。前日までは通ってた。

新しい証明書を発行して、SPごとに登録し直した。
freee、Salesforce、M365、SmartHR の4つ。全部やり直しでけっこう時間かかった。
登録後に自分のアカウントでログイン確認してOK。

9:55 に全社アナウンス出して収束。対応時間は3時間半くらい。

※次回のために：証明書の有効期限は監視に入ってないので毎年これが起きる。
　監視追加はベンダー見積待ち。
```

**このサンプルで確認すること**：手順としては「証明書を発行して各 SP に登録する」の一言ですが、実際に別の担当者が再現するには足りない情報が大量にあります。IdP 管理画面の場所、必要な権限、SP ごとの登録先画面、作業中にログインできなくなる利用者への周知、切り戻しの可否——これらが `【要追記】` として列挙されるのが期待される挙動です。

## 記録 B：ディスク領域不足からの復旧

```
対応記録 / INC-2026-0612-01
担当：宮本
受付：2026-06-12 06:05

朝のバッチ結果確認で NIGHTLY_SALES_AGG が ABEND してるのを発見。
ログ見たら ERR-DB-0412、TS_WORK が満杯。

df で見たら 96%。/archive の古いログを外部ストレージに退避して 71% まで下げた。
9月と1月にも同じことやってる。ローテーション直さないと毎回これ。

領域確保してから NIGHTLY_SALES_AGG を手動再実行、続けて後続3本も順番に流した。
売上データは 8:40 に反映完了。経理部には先に連絡入れておいた。

トータル2時間半。
```

**このサンプルで確認すること**：手順としては具体的ですが、`df` をどのサーバーで実行するのか、退避先の外部ストレージはどこか、手動再実行のコマンドは何か、後続ジョブの実行順序はどう確認するのか、といった情報がありません。また「9月と1月にも同じことやってる」という記述から、**注意事項に再発の履歴と恒久対策の必要性**が書き起こされるのが望ましい挙動です。
