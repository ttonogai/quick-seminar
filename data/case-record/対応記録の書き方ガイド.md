# 対応記録の書き方ガイド

文書番号: HD-GUIDE-2026-02
管理部門: 情報システム部 ヘルプデスク課

対応記録は、後から別の担当者が読んで**同じ対応を再現できること**を目的に書きます。以下のルールに従ってください。

## 優先度の判定基準

上から順に判定し、最初に当てはまったものを採用します。

| 優先度 | 判定基準 |
|--------|----------|
| 緊急 | 製造ライン・出荷など事業活動が停止している／全社または1部門全体が業務停止している／外部取引先との連携が停止している |
| 高 | 特定業務が実施できない状態が続いている／締め処理や納期など期限が迫っている／複数名に同一事象が発生している |
| 中 | 業務は継続できるが著しく非効率になっている／代替手段はあるが手間がかかる |
| 低 | 業務影響がない／操作方法の照会／申請対応／期限に余裕がある依頼 |

判定に迷う場合は**高いほうを選び**、「対応内容」の冒頭に判定根拠を1行で記載します。

## 記載ルール

### 件名
- 「対象システム＋症状」の形で書く
- 依頼者の言葉をそのまま使わず、事象として表現する
- 悪い例：`ログインできません（至急）` / 良い例：`経費精算システムでSSO認証エラーによりログイン不可`

### 対応内容
- 実施した確認・操作を**時系列で**書く
- 「〜を確認」「〜を実施」と、行為として書く
- 推測を断定形で書かない。推測は「〜の可能性を確認した」と書く
- 悪い例：`パスワードの入力ミスだった` / 良い例：`パスワードの入力誤りの可能性を確認したが、複数名で同一事象が発生していたため別要因と判断`

### 解決策
- 依頼者の事象が解消した方法を書く
- 未解決の場合は、現時点の状況と次のアクションを書く
- 「再起動して直った」で終わらせず、**なぜ直ったか**まで書く

### 依頼者向け回答
- 専門用語を避け、依頼者が次に何をすればよいかを明記する
- 原因が未確定の段階でも、いま何が分かっていて、次に何をするかを伝える
- 社内の体制や責任の所在に触れる表現は書かない

### 禁止事項
- 個人名を原因として記載しない（`◯◯さんの操作ミス` のような書き方はしない）
- 未確認の推測を事実として記載しない
- 選択肢が定義されている項目に、定義外の値を書かない
- 判断できない項目を空欄のままにしない（**判断できない場合は「要確認」と記載する**）

## 情報が足りないときの聞き返し方

問い合わせ内容だけでは分類・原因が特定できない場合は、次の観点で依頼者に確認します。**推測で埋めてはいけません。**

| 観点 | 確認すること |
|------|--------------|
| いつ | 発生日時。いつから発生しているか。以前は正常だったか |
| 誰が | 自分だけか、他の人にも起きているか。部門全体か |
| 何が | 対象システム名・端末の管理番号・対象の機能や画面 |
| どうなる | 画面に表示されるメッセージの全文。どの操作で発生するか |
| 業務影響 | 業務が止まっているか。代替手段があるか。期限があるか |
| 直前の変化 | パスワード変更・端末交換・設定変更・アプリ更新などの直前の出来事 |

## 類似ケースの活用

新規ケースを起票する前に、過去ケース履歴から類似事例を検索します。

- 同一の**事象＋原因区分**の組み合わせで検索する
- 類似ケースがある場合は、ケース番号を「類似ケース」項目に記載する
- **同一事象が 3 回以上発生している場合は、再発防止策として FAQ 化または恒久対策を必ず記載する**
